PC Sandbox Switcher and Submission Validator are deployment/testing tools covered by RG-GDK-022. The April MSIXVC2 and native ARM64 libraries are previews and are excluded from the stable release gate. Keep per-game performance or compatibility findings in that game's repository, with a linked SDK issue for shared fixes.

The next implementation order is: prove RG-GDK-002, integrate GameInput/XAudio2 and PC lifecycle at their existing boundaries, add PIX profiling to the D3D12 baseline, then decide DirectStorage from measured I/O. The audit is a scope and dependency map; it does not claim any GDK runtime, PIX capture or DirectStorage validation has passed.

## ARM64 PC build and package path

Microsoft's [new GDK layout guide](https://learn.microsoft.com/en-us/gaming/gdk/docs/gdk-dev/pc-dev/overviews/gdk-new-layout?view=gdk-2604) describes a shared `windows/include` tree and architecture-specific `windows/lib/arm64` and `windows/bin/arm64` trees. For MSBuild projects it says to enable `GDKCrossPlatform`, create ARM64 Debug/Release configurations, switch library and copied-DLL paths to `arm64`, and update XSAPI references to the v143 library. ReXGlue uses CMake, so RG-GDK-030 must express equivalent paths and target selection in its own toolchain rather than copying MSBuild properties. Microsoft's [April 2026 notes](https://learn.microsoft.com/en-us/gaming/gdk/docs/gdk-dev/whatsnew/whats-new?view=gdk-2604) call the native ARM64 GDK libraries a testing-only preview; the [release notes](https://learn.microsoft.com/en-us/gaming/gdk/docs/gdk-dev/whatsnew/release-notes?view=gdk-2604) remove VS2019 ARM64 template configurations and require VS2022 or later.

The installed `260404` edition has `windows/lib/arm64/xgameruntime.lib` and ARM64 native extension libraries/DLLs. The Windows SDK has ARM64 system libraries, but the installed VS Community and Build Tools instances do not have the ARM64 MSVC CRT libraries or cross compiler. The current `win-arm64` preset inherits an x64 host compiler selection and changes `-march`; it has not been proven to emit ARM64 PE binaries. Native ARM64 Windows hardware is also unavailable locally. These are setup and validation gaps, not evidence that the SDK cannot support ARM64.

For packaging, Microsoft's [`Executable` schema](https://learn.microsoft.com/en-us/gaming/gdk/docs/reference/system/microsoftgameconfig/elements/microsoftgameconfig-element-executable?view=gdk-2604) allows `Architecture="ARM64"` and `Architecture="x64"`, but requires the x64 executable when ARM64 is present (otherwise package error `0x89245212`). April 2026 Update 4 fixed `wdapp register` selecting the wrong executable on ARM64 for dual-architecture games. RG-GDK-031 must therefore verify the exact installed update and the executable actually launched, not just package creation. Neither cross-compilation nor x64 emulation constitutes native ARM64 gameplay or GPU validation.
